# CF 优选 IP 自动维护 v2

自动从多个源聚合候选 IP，经**真实存活验证 + 本机实测**后输出精选清单。

订阅地址（上传 GitHub 后）：

```
https://raw.githubusercontent.com/你的用户名/cf-select/main/ip.txt
```

## 相比 v1 改了什么

| 问题 | v1 的表现 | v2 的处理 |
|---|---|---|
| 验证结果造假 | log 写「通过 82/82」，ip.txt 里 colo 全是 `?` | verified / unverified 彻底分开，未验证的绝不进 TOP |
| 计票虚高 | 同一 IP 多端口重复计票，3 个源算出 31 票 | 同源同 IP 只投一票，票数 = 独立源个数 |
| 混入非节点 IP | `162.159.197.1` 排在 TOP1，那是 CF 的 DNS 后端 | 排除 162.159.197/198.x、1.1.1.x、1.0.0.x |
| 端口写死 | 解析时记录真实端口，输出却固定 `:443` | 非 443 直接丢弃，输出恒为 443 |
| 验证方式错 | urllib 请求 `https://{ip}/`，SNI 是 IP，CF 不认，必然失败 | 手动握手，SNI 设为 `www.cloudflare.com` |
| 拉源串行 | 6 个源一个超时拖死全部（实测 5/6 失败） | 并发拉取 + 每源重试 3 次 |
| 空结果冲库 | 验证失败也照样覆盖 ip.txt | 通过数 < 3 时保留旧文件不动 |

## 实测数据（2026-11-10）

**源不重叠**：62 个候选里没有一个 IP 被两个源同时收录，票数全是 1。
所谓「共识打分」在这份数据上等于随机排序，所以 v2 的最终排序交给本机实测，不交给票数。

**延迟 ≠ 可用**：延迟最低的 `35.78.243.103`（149ms / 东京）下载速度是 **0**。
只按延迟排序会选出带宽为 0 的废 IP，所以必须两轮筛。

**波动大**：同一个 `172.67.66.245`，两轮测速分别是 1.86MB/s 和 19.6MB/s。
所以最终保留 6 个节点做冗余，让客户端自己挑最快的。

## 两步走

```
第 1 步（云端）  GitHub Actions ──▶ ip_all.txt   拉源 + 去重 + trace 验活
第 2 步（本地）  local_check.bat ──▶ ip.txt       延迟 + 下载双实测
```

云端 runner 在境外，它能验「这个 IP 是不是活的 CF 节点」，但测不出你这条宽带快不快。
所以 Actions 只负责产出候选池，最终排序必须在你自己的网络上跑。

## 上手

### 一次性准备

1. GitHub 新建 **Public** 仓库（如 `cf-select`）
2. 上传 `scripts/`、`.github/` 两个文件夹（`cfst.exe` 不要传，8MB 且 GitHub 用不上）
3. Settings → Actions → General → Allow all actions
4. Actions 页 → 「更新CF优选IP」→ Run workflow 手动跑一次
5. 跑完仓库根目录出现 `ip_all.txt`

### 每天（可选，本地）

把仓库里的 `ip_all.txt` 下载到本目录，双击 `local_check.bat`，它会：

1. 提取纯 IP 列表
2. 跑 cfst 延迟测速（54 个约 20 秒）
3. 取延迟最好的 15 个跑下载测速（约 2 分钟）
4. 筛出「丢包 ≤0.25 / 延迟 <400ms / 下载 ≥5MB/s」的，按下载速度排序
5. 写进 `ip.txt`，不足 3 个时保留旧文件不覆盖

## 输出文件

| 文件 | 内容 | 用途 |
|---|---|---|
| `ip.txt` | 本机实测精选 TOP6 | **订阅用这个** |
| `ip_all.txt` | Actions 验活通过的 IP | 本地实测的输入 |
| `backup.txt` | 未通过验活的 | 仅供排查，别用 |
| `meta.json` | 每次运行统计 | 看运行是否正常 |
| `log.txt` | 完整日志（追加） | 出问题看这里 |
| `latency.csv` / `result.csv` | cfst 原始结果 | 复核用 |

`ip.txt` 格式：`IP:443#序号|机房|延迟|速度`，例如：

```
162.159.137.183:443#01|HKG|205ms|23.4MB/s
```

## 调参

`scripts/bestcf.py` 顶部：

- `TOP_N` — 云端候选数量上限
- `CANDIDATE_LIMIT` — 进入验活的候选上限，默认 60
- `MIN_ACCEPT` — 低于这个通过数就不覆盖 ip.txt，默认 3
- `SOURCES` — 增删源

`scripts/local_check.py` 顶部：

- `TOP_N` — 最终保留几个节点，默认 6
- `LAT_LIMIT` — 延迟上限，默认 400ms
- `SPEED_MIN` — 下载下限，默认 5MB/s
- `PRE_PICK` — 进入下载测速的候选数，默认 15

## 已知限制

- GitHub Actions 的 cron 在高峰期可能延迟 10-40 分钟，不保证准点
- 公共仓库 60 天无提交会被暂停定时任务；`meta.json` 每次运行都会更新时间戳，必定产生提交，不会休眠
- 测速有随机性，单次结果不代表长期表现，所以保留多个节点做冗余
- 源之间可能互相抄，票数高不等于快，最终以本地实测为准
